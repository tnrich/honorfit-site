不用 AccessibilityService 打造 Android App 屏蔽工具

从一个已上架的 App 来看 UsageStatsManager、前台服务和叠加窗口。作者：Thomas Willheim · 2026 年 11 月 9 日

我做了 HonorFit，一个靠做俯卧撑赚屏幕使用时间的 App 屏蔽工具（诚信制，不用摄像头）。第一个 Android 版本屏蔽 App 的方式跟大多数 Android 屏蔽工具一样：用 AccessibilityService。8 月的时候我把它整个拔掉，换成 UsageStatsManager、一个前台服务和一个叠加窗口。屏蔽变得稍微没那么硬，新手引导变得一点都不吓人，Play 的审核也简单多了。

下面是这个架构长什么样子，还有一路上踩到的坑。所有代码都是写在一个本机 Expo module 里的 Kotlin，但这里讲的东西没有一样是 React Native 专属的。

为什么要去掉无障碍 API

无障碍服务是 Android 上最强的工具。每次窗口变化你都会立刻收到通知，而 performGlobalAction(GLOBAL_ACTION_HOME) 可以当场把用户踢出被屏蔽的 App。这就是为什么这么多屏蔽工具都用它。代价是：

  • 权限提示超吓人。Android 会告诉用户，这个 App 可以看到屏幕上的所有东西，还能代替他们操作。对一个主打“数据都不会离开你的手机”的 App 来说，第一天就要求这个权限很难看，很多人当场就放弃了。
  • Google Play 把它当成敏感 API。如果你不是无障碍工具，就需要在 App 里放显眼的揭露说明、在 Play Console 填声明，还要审核人员同意你的用途没问题。我连揭露说明的对话框都做好了，但我宁愿根本不需要它。
  • 它看到的东西远超过屏蔽工具需要的。屏蔽工具只需要知道一件事：现在前台是哪个 App。

而这件事在别的地方也拿得到：数字健康（Digital Wellbeing）背后用的那些使用事件。

整体架构

三个权限，全部由用户在“设置”里授予：

权限用途
PACKAGE_USAGE_STATS（“使用情况访问权”）读取 UsageEvents，知道前台是哪个 App。这个权限不能在运行阶段授予；你要把用户带到设置页面，再检查 app-op。
SYSTEM_ALERT_WINDOW（“显示在其他应用程序上层”）在被屏蔽的 App 上面画出锁定界面。
FOREGROUND_SERVICE_SPECIAL_USE监控服务。屏蔽 App 不属于任何列出来的前台服务类型，所以用 specialUse，再加一个说明原因的子类型字符串。

各个部分：

  • ForegroundMonitorService 只有在有东西需要运行的时候才会跑（屏蔽列表不是空的，而且已授予使用情况访问权）。它每秒问一次 UsageStatsManager 现在前台是什么，而且只在屏幕亮着的时候。被屏蔽但还有时间的 App 会扣掉存着的余额；扣到零就显示叠加窗口。
  • 它必须显示的通知就是额度显示（“还剩 12 分钟”），所以 Android 硬塞给你的东西也做了正事。
  • 所有状态都存在 SharedPreferences，不在 JS 里。React Native 的运行环境大部分时间都是死的，服务必须在这种情况下继续运作。JS 端通过 module 存入时间、读取余额；运行屏蔽则由服务负责。

服务在 manifest 里的设置：

<service
  android:name=".ForegroundMonitorService"
  android:exported="false"
  android:foregroundServiceType="specialUse">
  <property
    android:name="android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE"
    android:value="User-configured app blocking for digital wellbeing: monitors
      which app is in the foreground (UsageStats) so apps the user chose to block
      can be locked when their earned screen time runs out." />
</service>

你还要在 Play Console 的前台服务声明里说明为什么用 specialUse。两边讲同一套说法会有帮助。

轮询 UsageStats（还有它的写入延迟）

内核循环很小。扫描上次轮询之后的事件，留下最后一个 MOVE_TO_FOREGROUND 的套件（它跟 ACTIVITY_RESUMED 是同一个常数，在 API 29 改了名字）：

val end = System.currentTimeMillis()
val events = usm.queryEvents(windowStart, end)
val event = UsageEvents.Event()
while (events.hasNextEvent()) {
  events.getNextEvent(event)
  if (event.eventType == UsageEvents.Event.MOVE_TO_FOREGROUND) {
    currentForeground = event.packageName
  }
}
// 下次重新扫描最后 15 秒：见下文。
windowStart = end - REQUERY_OVERLAP_MS
handleForeground(currentForeground)

跟无障碍事件比起来有个不错的附带好处：键盘和通知栏都不是 activity，所以它们永远不会被误判成“用户离开了 App”。

地雷：事件会晚到

我的第一版让时间窗严格往前推进：每次轮询查找 [lastEnd, now]。大部分时候都没问题，结果在一支刚冷开机的手机上，第一次打开被屏蔽的 App 完全没被看到。UsageStats 把事件写进保存区会有延迟，所以一个时间戳是 10:00:00.900 的事件，可能在一次已经涵盖到 10:00:01 的轮询之后才出现。严格往前推的时间窗会永远跳过它。

解法：每次轮询都重新扫描最后一段重叠区间（我用 15 秒）。同一个事件看到两次没有坏处，因为不管怎样，时间窗里最后一次 resume 说了算。晚超过 15 秒才进来的事件还是会漏掉，但我还没看过。

地雷：第一次轮询要往回看很久

服务启动时（重新启动后，或屏幕亮起时）没有“最后已知的 App”。如果用户已经在 TikTok 里待了 20 分钟，而第一次轮询只往回看一分钟，在他切换 App 之前什么都看不到。所以第一次轮询会扫描最近一小时。这样做是安全的，因为桌面启动器也是一个 activity：最后一个 resume 的，就真的是现在在前台的。

地雷：访问权被撤销时看起来就是一片安静

如果用户在服务运行时关掉使用情况访问权，queryEvents 不会丢例外，只会什么都不返回。你最后读到的结果（“Instagram 在前台”）就过时了，余额会一直扣下去。所以每次轮询都会先检查 app-op，如果权限没了就停止计时：

fun hasUsageAccess(context: Context): Boolean {
  val appOps = context.getSystemService(Context.APP_OPS_SERVICE) as AppOpsManager
  val mode = appOps.checkOpNoThrow(
    AppOpsManager.OPSTR_GET_USAGE_STATS, Process.myUid(), context.packageName)
  return mode == AppOpsManager.MODE_ALLOWED
}

屏幕关掉就停

屏幕关掉时，服务会把进行中的使用时段结算，然后完全停止轮询。屏幕关着不会有人在用 App，而一个只在你看手机时才跑的 1 Hz 循环很省。屏幕重新亮起后的第一次轮询也会处理换日（午夜重置、每日基本额度），所以它会在用户打开被屏蔽的 App 之前就完成，就算他们从来不打开 HonorFit 也一样。

锁定叠加窗口

没有无障碍就没有 GLOBAL_ACTION_HOME，所以你没办法把用户踢出 App，只能把它盖住：一个 TYPE_APPLICATION_OVERLAY 窗口，上面有“赚更多时间”按钮和“回到主屏幕”按钮。

  • 盖住整个屏幕。默认情况下，叠加窗口会被系统栏缩进，被屏蔽的 App 会从边缘露出来。FLAG_LAYOUT_NO_LIMITS 可以解决。FLAG_LAYOUT_IN_SCREEN 在 API 30 已被淘汰，所以只在 R 以下加上它。
  • “回到主屏幕”必须真的回到主屏幕。只把叠加窗口隐藏，被屏蔽的 App 又会露出来，下一次轮询又会把锁放回去。改成启动桌面启动器： 
    startActivity(Intent(Intent.ACTION_MAIN).apply {
  addCategory(Intent.CATEGORY_HOME)
  addFlags(Intent.FLAG_ACTIVITY_NEW_TASK)
})
  • 先启动，再隐藏。“赚更多时间”按钮会打开 HonorFit，这是从后台启动 activity。Android 允许这么做，是因为 App 有一个看得见的叠加窗口。所以要在叠加窗口还显示的时候启动 activity，然后再把它移除。顺序反过来，启动就会被默默挡掉。
  • 没有叠加权限？照样计时。如果没有授予“显示在其他应用程序上层”，服务还是会诚实地扣余额，只是在权限回来之前画不出锁定界面。

让服务活下去

这是最花时间才能弄对的部分，而且大多跟你的代码无关。

START_STICKY 不够

Samsung 的“休眠中的应用程序”、MIUI、OnePlus 这些系统会杀掉后台服务，然后把 sticky 重启吞掉。屏蔽工具是最糟的情况：大家还有时间的时候不会打开它，所以监控不见了也没有东西会发现。HonorFit 设了一个每 15 分钟一次、不精确、不唤醒的重复闹钟，重新把服务拉起来。它从来不会唤醒手机，而屏幕关着时被延后的闹钟，会在屏幕亮起后不久触发，那正是监控最重要的时候。

Android 12 以上不一定让你启动它

从后台（闹钟、sticky 重启）启动前台服务会丢出 ForegroundServiceStartNotAllowedException，除非你有豁免。这里有两个相关的：用户已经关掉这个 App 的电池优化，或 App 持有 SYSTEM_ALERT_WINDOW（这个只在 Android 15 之前有用）。所以：

  • 接住这个例外，安静地退出。让进程当掉对谁都没好处，下次打开 App 时服务反正也会启动。
  • 请用户把电池用量设成“无限制”。HonorFit 的“设置”里有一张“后台运行稳定性”卡片，会带他们到正确的页面。在某些手机上，这个设置就是能不能用的差别。

重新开机和更新

一个接收 BOOT_COMPLETED 和 MY_PACKAGE_REPLACED 的 receiver 会重新启动监控。第二个很容易忘记：Play 自动更新会杀掉你的进程，而且从来不会重启它的服务，所以没有它的话，每次更新都会默默把你的屏蔽工具关掉，直到用户打开 App 为止。这两个广播都不受后台启动限制，而且 exported="false" 的 receiver 一样收得到。

其他小事

  • 有些 App 绝对不能被屏蔽：设置、时钟（闹钟！）和个人安全，还有各家厂商的版本，例如 Samsung 的时钟应用。要在原生代码里把它们从屏蔽列表滤掉，不能只在选择器里处理。
  • 服务在没有 JS 的情况下运行，所以不能调用 t()。App 会把叠加窗口和通知的字符串，用目前的语言推进 SharedPreferences，在字符串送到之前，服务会先用英文。
  • 服务重启期间一直开着的使用时段，在服务死掉的那段时间没办法扣时间。启动时，把经过的时间结算（有上限），再开始一个新的时段，这样就没有人会因为服务不在而被扣到它没看到的时间。
  • Android 14 以上可以让用户划掉前台服务的通知。服务会持续更新它（有做去重，所以不会每秒重新发一次），所以它会再回来。

取舍

这个做法比无障碍软，这点我想先讲清楚：

  • 被屏蔽的 App 在叠加窗口出现之前，最多会露出一个轮询间隔（大约一秒）。
  • 被屏蔽的 App 会在叠加窗口底下继续运行。如果原本在播视频，在你点“回到主屏幕”之前还是听得到声音。
  • 它要看手机厂商愿不愿意放过你的服务，这也是为什么电池设置这么重要。

对一个诚信制的屏蔽工具来说，这是正确的取舍。HonorFit 并不想做到牢不可破。真的想作弊的人，直接记没做的次数就好了。重点是让你停一下、付出一点代价，而不是把你关起来。换来的是一个写着“使用情况访问权”而不是“完全控制”的权限页面、简单得多的 Play 审核，以及一个只读一样东西的服务：前台 App 的包名。

如果你也在做 iOS，那边完全是另一个世界。我写了Apple 的 Screen Time 文档没告诉你的事。
