Affiliatecodes voor een indie-app zonder backend

Eén verborgen in-app-aankoop per partner, en de stores doen de boekhouding. Door Thomas Willheim · 20 november 2026

Hoi allemaal! HonorFit is de app blocker waarmee je je schermtijd verdient met push-ups, op erewoord. Er zijn geen accounts en er is geen server. Je data blijft op je telefoon, want er is geen andere plek waar ze heen kan.

Toen vroeg een creator of ik een affiliateprogramma had. Dat wilde ik wel: zij krijgen een code, hun publiek krijgt 20% korting op Pro Levenslang, en zij krijgen 50% van wat ik verdien aan elke verkoop. Maar elke affiliateopzet die ik bekeek, gaat uit van een backend die codes opslaat, kliks bijhoudt en aankopen aan partners koppelt. Ik wilde er niet speciaal hiervoor een bouwen, en ik wilde al helemaal niet ‘er gaat niks van je telefoon af’ breken om het te doen.

Dit is wat ik in plaats daarvan heb gedaan. Het werkt op iPhone en Android, en het is een kleine aanpassing aan de paywall plus één script op mijn laptop.

Waarom niet de eigen promocodes van de stores?

Apple heeft offer codes, maar de promocodes van Google Play voor eenmalige producten kunnen het item alleen gratis weggeven. Er bestaat geen ‘20% korting’. Ik wilde één code die in beide stores hetzelfde werkt, dus de codes van de stores vielen af.

En zelfs met kortingen is er een tweede probleem: ik moet elke maand weten van wie de code was bij elke verkoop, om mensen te kunnen betalen.

De truc: elke partner krijgt een eigen product

HonorFit verkoopt Pro Levenslang al als eenmalige aankoop, honorfit_pro_lifetime, voor $19,99. Elke partner krijgt een kopie van dat product met zijn code in de ID, voor $15,99:

honorfit_pro_lifetime            $19.99   (wat iedereen ziet)
honorfit_pro_lifetime_p_alex20   $15.99   (alleen met de code ALEX20)

Die ene beslissing regelt de drie taken die normaal een backend zou doen:

  • De code controleren. De code is de product-ID. De app vraagt de store of dat product bestaat. Zo ja, dan is de code echt.
  • De korting. Dat is gewoon de prijs van het product, die de store voor elk land lokaliseert, net als elke andere prijs.
  • Attributie. De verkooprapporten van Apple en Google tonen al elke verkoop per product-ID. Een verkoop van ..._p_alex20 is een verkoop van ALEX20.

Niemand ziet deze producten tenzij hij een code intypt. In-app-aankopen verschijnen in geen van beide stores in de listing, tenzij je ervoor kiest ze te promoten, dus de partnerproducten bestaan alleen voor mensen die de code kennen.

De kant van de app

De paywall kreeg een klein linkje ‘Heb je een partnercode?’ onder ‘Aankopen herstellen’. Tik je erop, dan verschijnt er een tekstveld. Vult iemand een code in, dan maak ik die op en vraag ik de store om dat product. Dit gebruikt expo-iap, maar met StoreKit of Play Billing rechtstreeks is het hetzelfde idee:

const PARTNER_PREFIX = 'honorfit_pro_lifetime_p_';

// "alex-20 " -> "ALEX20". Veel meer past er niet in een product-ID.
export function normalizePartnerCode(input: string) {
  const code = input.replace(/[\s-]/g, '').toUpperCase();
  return /^[A-Z0-9]{3,20}$/.test(code) ? code : null;
}

export async function lookupPartnerCode(code: string) {
  const sku = PARTNER_PREFIX + code.toLowerCase();
  const products = await fetchProducts({ skus: [sku], type: 'in-app' });
  const product = products?.find((p) => p.id === sku);
  return product ? { code, sku, price: product.displayPrice } : null;
}

Komt het product terug, dan toont de Levenslang-kaart $19,99 $15,99 en koopt de koopknop het product van de partner in plaats van het gewone. Zo niet, dan zegt het veld dat de code niet geldig is. Een fout van de store krijgt een eigen melding, zodat een telefoon zonder verbinding iemand niet vertelt dat zijn echte code nep is.

Het laatste stuk is het recht op Pro. Overal waar de app vroeg ‘is dit een Pro-product?’, vergeleek hij vroeger met een lijst van twee ID's. Nu is het een prefixcontrole, dus de purchase listener en ‘Aankopen herstellen’ behandelen een partneraankoop precies zoals Levenslang:

export const isProSku = (sku: string) =>
  sku === MONTHLY_SKU || sku === LIFETIME_SKU || sku.startsWith(PARTNER_PREFIX);

Omdat codes bij de store gecontroleerd worden, heb je voor een nieuwe partner nooit een app-update nodig. Er staat geen lijst met codes in de app die je bij moet houden.

De producten aanmaken via de API

Voor elke partner met de hand een product aanmaken in twee consoles gaat snel vervelen, dus bun run affiliate add ALEX20 "Alex" "alex@example.com" doet ze allebei:

App Store Connect

  1. Maak de in-app-aankoop (non-consumable) aan met de product-ID van de partner.
  2. Kopieer de weergavenaam en beschrijving van het Levenslang-product in elke taal.
  3. Stel een Amerikaanse basisprijs van $15,99 in. Apple rekent daaruit de andere landen uit.
  4. Kopieer de beschikbaarheid per land van Levenslang, upload een screenshot voor de review, en schrijf een reviewnotitie die de reviewer precies vertelt waar het codeveld zit en welke code hij moet intypen.

Daarna stuurt bun run affiliate submit ALEX20 het naar App Review. Elk partnerproduct wordt apart beoordeeld, meestal binnen een dag of twee. Apple keurt alleen een in-app-aankoop goed waar de reviewer ook echt bij kan, dus het codeveld moet eerst in de live app staan.

Google Play

Mijn eerste poging gebruikte het oude inappproducts-endpoint, dat een 403 teruggaf met de mededeling dat ik moest migreren. Eenmalige producten zitten nu onder oneTimeProducts, waar een product een of meer aankoopopties heeft. Het script:

  1. Kopieert de listings en belastinginstellingen van Levenslang naar een nieuw eenmalig product.
  2. Draait pricing:convertRegionPrices op $15,99 om een prijs voor elke regio te krijgen.
  3. Maakt één aankoopoptie van het type ‘buy’ met die prijzen en activeert die daarna met purchaseOptions:batchUpdateStates.

Play-producten gaan meteen live, zonder review.

Partners uitbetalen op basis van de rapporten van de stores

Eén keer per maand haalt bun run affiliate report 2026-11 de rapporten van beide stores op en rekent uit wat elke partner verdiend heeft:

  • Apple: het maandelijkse Sales Summary-rapport uit de App Store Connect API. Elke rij bevat de SKU, het aantal stuks en de opbrengst voor de ontwikkelaar in de valuta van de koper. Ik reken de opbrengst om naar Amerikaanse dollars tegen de wisselkoers van de laatste dag van de maand. Apple betaalt uit tegen zijn eigen koersen, dus dit is een schatting, maar wel dichtbij genoeg om op uit te betalen. (Addertje: vraag rapportversie 1_0 op. 1_1 gaf voor dit rapport een 400.)
  • Google: het maandelijkse earnings-rapport, een zip in de Cloud Storage-bucket van je Play Console. Daarin staan elke betaling, Google-fee, belasting en terugbetaling al als aparte rijen, dus als je ze per SKU optelt, krijg je het echte nettobedrag.

Elke partner krijgt 50% van het nettobedrag, met nul als ondergrens, en het script schrijft een CSV waarmee ik kan uitbetalen.

Addertje bij Play: het serviceaccount heeft ‘View financial data’ nodig in Play Console om earnings-rapporten te downloaden. Nadat ik dat had aangezet, kon het account de bestanden wel opsommen, maar kreeg het ongeveer een dag lang nog een 403 bij het downloaden. Gebeurt dat bij jou ook, wacht dan even voordat je aan de rechten van de bucket gaat sleutelen.

De nadelen

  • Eén product per partner. Prima voor een handvol creators. Voor honderden wil je sowieso echte infrastructuur.
  • Elk Apple-product wordt gereviewd. De code van een nieuwe partner werkt dezelfde dag op Android en een dag of twee later op iPhone.
  • Codes zijn openbaar. Iedereen kan ALEX20 intypen, en daar gaat het juist om. De programmavoorwaarden sluiten kortingssites en kopen met je eigen code uit, en terugbetalingen gaan van latere uitbetalingen af.
  • Geen kliktracking. Ik weet welke codes verkocht hebben, niet wie waarvandaan kwam. Voor een app die zijn gebruikers niet volgt, vind ik dat prima.

Bonus: bevestig aankopen die buiten je app zijn gedaan

Deze kwam in dezelfde week voorbij. Als iemand een Google Play-promocode inwisselt in de Play Store, gebeurt de aankoop buiten je app, dus je purchase listener ziet hem nooit. Google betaalt elke aankoop terug die niet binnen 3 dagen bevestigd (acknowledged) is. HonorFit controleert op Android nu bij het opstarten en elke keer dat de app weer op de voorgrond komt welke aankopen je bezit, bevestigt de aankopen die nog niet bevestigd zijn, en ontgrendelt Pro.
