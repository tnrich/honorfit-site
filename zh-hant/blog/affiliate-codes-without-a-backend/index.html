沒有後端的獨立 App 怎麼做聯盟代碼

每個合作夥伴一個隱藏的 App 內購買項目，帳就交給商店來記。作者：Thomas Willheim · 2026 年 11 月 20 日

大家好。HonorFit 是一款用伏地挺身賺螢幕使用時間的 App 封鎖工具，採誠實制。它沒有帳號，也沒有伺服器。你的資料留在手機上，因為它根本沒有別的地方可去。

後來有位創作者問我有沒有聯盟行銷計畫。我也想做：創作者拿到一組代碼，他們的粉絲買終身版 Pro 打八折，創作者則從每筆銷售拿到我收入的 50%。但我看過的每一種聯盟行銷做法，都預設你有一個後端來儲存代碼、追蹤點擊、把購買對應到合作夥伴。我不想為了這件事專門做一個後端，更不想為此打破「什麼都不會離開你的手機」這個原則。

所以我改用下面這個做法。iPhone 和 Android 都能用，內容只有付費牆的一個小改動，加上我筆電上的一支腳本。

為什麼不用商店自己的優惠代碼？

Apple 有優惠代碼（offer code），但 Google Play 的一次性產品優惠代碼只能把商品免費送出去，沒有「打八折」這種選項。我想要一組在兩個商店都一樣好用的代碼，所以商店代碼就出局了。

而且就算能打折，還有第二個問題：我每個月都得知道每筆銷售是來自誰的代碼，才能付錢給大家。

訣竅：每個合作夥伴都有自己的商品

HonorFit 本來就把終身版 Pro 當成一次性購買項目 honorfit_pro_lifetime 在賣，價格 19.99 美元。每個合作夥伴都會拿到這個商品的一份複本，ID 裡帶著他們的代碼，價格設為 15.99 美元：

honorfit_pro_lifetime            $19.99   （所有人看到的商品）
honorfit_pro_lifetime_p_alex20   $15.99   （只有輸入代碼 ALEX20 才會出現）

光是這一個決定，就搞定了平常要靠後端做的三件事：

  • 驗證代碼。代碼就是商品 ID。App 去問商店這個商品存不存在，存在的話，代碼就是真的。
  • 折扣。就是商品的價格而已，商店會像處理其他價格一樣，幫每個國家換算成當地價格。
  • 歸屬。Apple 和 Google 的銷售報表本來就會依商品 ID 列出每一筆銷售。..._p_alex20 的銷售，就是 ALEX20 的銷售。

除非輸入代碼，否則沒有人看得到這些商品。App 內購買項目只要你不主動推廣，就不會出現在任何一個商店的頁面上，所以合作夥伴商品只對知道代碼的人存在。

App 這一端

付費牆的「回復購買項目」下方多了一個小小的「有合作夥伴代碼嗎？」連結。點下去會出現一個文字欄位。使用者輸入代碼後，我先把它整理乾淨，再向商店查詢那個商品。這裡用的是 expo-iap，但直接用 StoreKit 或 Play Billing 也是同樣的概念：

const PARTNER_PREFIX = 'honorfit_pro_lifetime_p_';

// "alex-20 " -> "ALEX20"。商品 ID 也容不下太多其他字元。
export function normalizePartnerCode(input: string) {
  const code = input.replace(/[\s-]/g, '').toUpperCase();
  return /^[A-Z0-9]{3,20}$/.test(code) ? code : null;
}

export async function lookupPartnerCode(code: string) {
  const sku = PARTNER_PREFIX + code.toLowerCase();
  const products = await fetchProducts({ skus: [sku], type: 'in-app' });
  const product = products?.find((p) => p.id === sku);
  return product ? { code, sku, price: product.displayPrice } : null;
}

如果商品有回來，終身版的卡片就會顯示 19.99 美元 15.99 美元，購買按鈕也會改買合作夥伴的商品，而不是一般的那個。如果沒回來，欄位會顯示代碼無效。商店錯誤會有自己的訊息，這樣手機離線時，就不會跟人家說他手上真的代碼是假的。

最後一塊是權限判斷。App 裡所有問「這是不是 Pro 商品？」的地方，以前都是拿兩個 ID 的清單來比對。現在改成檢查前綴，所以購買監聽器和「回復購買項目」會把合作夥伴購買當成跟終身版一模一樣：

export const isProSku = (sku: string) =>
  sku === MONTHLY_SKU || sku === LIFETIME_SKU || sku.startsWith(PARTNER_PREFIX);

因為代碼是向商店查詢驗證的，新增合作夥伴完全不需要更新 App。App 裡沒有一份需要隨時更新的代碼清單。

用 API 建立商品

每多一個合作夥伴就要在兩個後台手動建一次商品，很快就會煩死，所以 bun run affiliate add ALEX20 "Alex" "alex@example.com" 會一次把兩邊都做好：

App Store Connect

  1. 用合作夥伴的商品 ID 建立 App 內購買項目（非消耗性）。
  2. 把終身版商品每種語言的顯示名稱和說明都複製過來。
  3. 設定 15.99 美元的美國基準價格，其他國家的價格由 Apple 自動換算。
  4. 複製終身版的國家／地區供應設定，上傳審查用的截圖，再寫一段審查備註，清楚告訴審查人員代碼欄位在哪裡、要輸入哪個代碼。

接著用 bun run affiliate submit ALEX20 送交 App 審查。每個合作夥伴商品都要個別審查，通常一兩天內完成。Apple 只會核准審查人員實際找得到的 App 內購買項目，所以代碼欄位得先出現在已上架的 App 裡。

Google Play

我第一次試的是舊的 inappproducts 端點，結果回了一個 403，叫我遷移。一次性產品現在放在 oneTimeProducts 底下，一個產品可以有一個以上的購買選項。腳本會：

  1. 把終身版的商店資訊和稅務設定複製到一個新的一次性產品。
  2. 對 15.99 美元執行 pricing:convertRegionPrices，取得每個地區的價格。
  3. 用這些價格建立一個購買選項，再用 purchaseOptions:batchUpdateStates 啟用它。

Play 的商品不用審查，馬上就會上線。

用商店報表付錢給合作夥伴

每個月一次，bun run affiliate report 2026-11 會抓兩個商店的報表，算出每個合作夥伴賺了多少：

  • Apple：App Store Connect API 的每月 Sales Summary 報表。每一列都有 SKU、數量，以及以買家幣別計算的開發者收益。我用當月最後一天的匯率把收益換算成美元。Apple 是用它自己的匯率付款，所以這只是估計值，但拿來付款已經夠接近了。（小陷阱：報表版本要指定 1_0。1_1 在這份報表上回了 400。）
  • Google：每月收益報表，是放在你 Play Console 的 Cloud Storage bucket 裡的一個 zip。每一筆扣款、Google 手續費、稅金和退款都已經是獨立的列，所以依 SKU 加總就能得到真正的淨收入。

每個合作夥伴拿淨收入的 50%，最低為零，腳本會輸出一份我可以直接拿來付款的 CSV。

Play 的小陷阱：服務帳戶要在 Play Console 裡有「查看財務資料」權限，才能下載收益報表。我開啟之後，這個帳戶已經可以列出檔案，但下載還是回 403，大概持續了一天。如果你也遇到這種情況，先等一等，再考慮去改 bucket 權限。

取捨

  • 每個合作夥伴一個商品。只有少數幾位創作者的話沒問題。如果有幾百位，反正你也會需要真正的基礎架構。
  • Apple 的每個商品都要審查。新合作夥伴的代碼在 Android 上當天就能用，在 iPhone 上則要晚一兩天。
  • 代碼是公開的。任何人都可以輸入 ALEX20，這正是重點。計畫條款禁止放上優惠券網站、禁止用自己的代碼購買，退款會從之後的分潤中扣除。
  • 沒有點擊追蹤。我知道哪些代碼賣出去了，但不知道誰從哪裡來。對一個不追蹤使用者的 App 來說，我覺得這樣很好。

加碼：確認在 App 外完成的購買

這是同一週剛好遇到的事。如果有人在 Play 商店兌換 Google Play 優惠代碼，購買是在你的 App 外完成的，所以你的購買監聽器永遠不會收到。Google 會把 3 天內沒有確認（acknowledge）的購買退款。現在 HonorFit 在 Android 上，每次啟動和每次回到前景時都會檢查已擁有的購買，確認還沒確認的那些，然後解鎖 Pro。
