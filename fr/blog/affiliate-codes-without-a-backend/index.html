Des codes d’affiliation pour une appli indé sans backend

Un achat intégré caché par partenaire, et les stores tiennent les comptes. Par Thomas Willheim · 20 novembre 2026

Salut tout le monde. HonorFit, c’est le bloqueur d’applis où tu gagnes ton temps d’écran avec des pompes, sur l’honneur. Il n’y a ni comptes ni serveur. Tes données restent sur ton téléphone parce qu’elles n’ont nulle part ailleurs où aller.

Et puis un créateur de contenu m’a demandé si j’avais un programme d’affiliation. J’en voulais un : il reçoit un code, sa communauté a 20 % de réduction sur Pro À vie, et il touche 50 % de ce que je gagne sur chaque vente. Mais tous les systèmes d’affiliation que j’ai regardés supposent un backend qui stocke les codes, suit les clics et relie les achats aux partenaires. Je ne voulais pas en construire un juste pour ça, et je ne voulais surtout pas casser le « rien ne quitte ton téléphone » pour y arriver.

Voilà ce que j’ai fait à la place. Ça marche sur iPhone et Android, et c’est un petit changement dans le paywall plus un script sur mon ordi portable.

Pourquoi pas les codes promo des stores ?

Apple a des codes d’offre, mais les codes promo de Google Play pour les produits à achat unique ne peuvent que donner l’article gratuitement. Pas de « 20 % de réduction ». Je voulais un seul code qui marche pareil sur les deux stores, donc les codes des stores étaient éliminés.

Et même avec des réductions, il y a un deuxième problème : je dois savoir de qui venait le code de chaque vente, chaque mois, pour payer les gens.

L’astuce : chaque partenaire a son propre produit

HonorFit vend déjà Pro À vie en achat unique, honorfit_pro_lifetime, à 19,99 $ US. Chaque partenaire reçoit une copie de ce produit avec son code dans l’ID, à 15,99 $ US :

honorfit_pro_lifetime            $19.99   (ce que tout le monde voit)
honorfit_pro_lifetime_p_alex20   $15.99   (seulement avec le code ALEX20)

Cette seule décision règle les trois tâches qu’un backend ferait normalement :

  • Vérifier le code. Le code est l’ID du produit. L’appli demande au store si ce produit existe. S’il existe, le code est valide.
  • La réduction. C’est juste le prix du produit, que le store adapte à chaque pays comme n’importe quel autre prix.
  • L’attribution. Les rapports de ventes d’Apple et de Google listent déjà chaque vente par ID de produit. Une vente de ..._p_alex20, c’est une vente d’ALEX20.

Personne ne voit ces produits sans taper un code. Les achats intégrés n’apparaissent sur la fiche d’aucun des deux stores, sauf si tu choisis de les mettre en avant, donc les produits partenaires n’existent que pour ceux qui connaissent le code.

Côté appli

Le paywall a gagné un petit lien « Tu as un code partenaire ? » sous Restaurer les achats. Quand on le touche, un champ de texte s’affiche. Quand quelqu’un saisit un code, je le nettoie et je demande ce produit au store. J’utilise expo-iap, mais l’idée est la même avec StoreKit ou Play Billing directement :

const PARTNER_PREFIX = 'honorfit_pro_lifetime_p_';

// "alex-20 " -> "ALEX20". Les ID de produit n'acceptent pas grand-chose d'autre.
export function normalizePartnerCode(input: string) {
  const code = input.replace(/[\s-]/g, '').toUpperCase();
  return /^[A-Z0-9]{3,20}$/.test(code) ? code : null;
}

export async function lookupPartnerCode(code: string) {
  const sku = PARTNER_PREFIX + code.toLowerCase();
  const products = await fetchProducts({ skus: [sku], type: 'in-app' });
  const product = products?.find((p) => p.id === sku);
  return product ? { code, sku, price: product.displayPrice } : null;
}

Si le produit revient, la carte À vie affiche 19,99 $ US 15,99 $ US et le bouton d’achat achète le produit du partenaire au lieu du produit normal. Sinon, le champ indique que le code n’est pas valide. Une erreur du store a son propre message, pour qu’un téléphone hors ligne ne dise pas à quelqu’un que son vrai code est faux.

La dernière pièce, ce sont les droits d’accès. Partout où l’appli se demandait « est-ce un produit Pro ? », elle comparait avec une liste de deux ID. Maintenant c’est une vérification de préfixe, donc l’écouteur d’achats et Restaurer les achats traitent un achat partenaire exactement comme À vie :

export const isProSku = (sku: string) =>
  sku === MONTHLY_SKU || sku === LIFETIME_SKU || sku.startsWith(PARTNER_PREFIX);

Comme les codes sont vérifiés auprès du store, ajouter un partenaire ne demande jamais de mise à jour de l’appli. Il n’y a aucune liste de codes dans l’appli à tenir à jour.

Créer les produits par API

Créer un produit à la main dans deux consoles pour chaque partenaire deviendrait vite pénible, donc bun run affiliate add ALEX20 "Alex" "alex@example.com" fait les deux :

App Store Connect

  1. Crée l’achat intégré (non consommable) avec l’ID de produit du partenaire.
  2. Copie le nom affiché et la description du produit À vie dans toutes les langues.
  3. Fixe un prix de base de 15,99 $ US aux États-Unis. Apple en déduit les autres pays.
  4. Copie la disponibilité par pays d’À vie, envoie une capture d’écran pour la vérification et rédige une note de vérification qui indique au vérificateur exactement où se trouve le champ du code et quel code taper.

Ensuite, bun run affiliate submit ALEX20 l’envoie à l’App Review. Chaque produit partenaire est vérifié séparément, en général en un ou deux jours. Apple n’approuve un achat intégré que si son vérificateur peut vraiment y accéder, donc le champ du code doit d’abord être dans l’appli publiée.

Google Play

Mon premier essai utilisait l’ancien endpoint inappproducts, qui a renvoyé un 403 me disant de migrer. Les produits à achat unique vivent maintenant sous oneTimeProducts, où un produit contient une ou plusieurs options d’achat. Le script :

  1. Copie les fiches et les paramètres de taxes d’À vie dans un nouveau produit à achat unique.
  2. Lance pricing:convertRegionPrices sur 15,99 $ US pour obtenir un prix pour chaque région.
  3. Crée une option d’achat avec ces prix, puis l’active avec purchaseOptions:batchUpdateStates.

Les produits Play sont en ligne tout de suite, sans vérification.

Payer les partenaires à partir des rapports des stores

Une fois par mois, bun run affiliate report 2026-11 récupère les rapports des deux stores et calcule ce que chaque partenaire a gagné :

  • Apple : le rapport mensuel Sales Summary de l’App Store Connect API. Chaque ligne contient le SKU, les unités et les revenus développeur dans la devise de l’acheteur. Je convertis les revenus en dollars US au taux de change du dernier jour du mois. Apple paie à ses propres taux, donc c’est une estimation, mais c’est assez proche pour payer avec. (Piège : demande la version de rapport 1_0. 1_1 renvoyait un 400 pour ce rapport.)
  • Google : le rapport mensuel des revenus, un zip dans le bucket Cloud Storage de ta Play Console. Il contient déjà chaque paiement, commission Google, taxe et remboursement sur des lignes séparées, donc les additionner par SKU donne le vrai net.

Chaque partenaire touche 50 % du net, plancher à zéro, et le script génère un CSV avec lequel je peux payer.

Piège côté Play : le compte de service a besoin de « Afficher les données financières » dans la Play Console pour télécharger les rapports de revenus. Après l’avoir activé, le compte pouvait lister les fichiers mais prenait encore un 403 en les téléchargeant pendant environ une journée. Si ça t’arrive, attends avant de te mettre à modifier les autorisations du bucket.

Les compromis

  • Un produit par partenaire. Ça va pour une poignée de créateurs. Pour des centaines, il te faudrait de toute façon une vraie infrastructure.
  • Chaque produit Apple est vérifié. Le code d’un nouveau partenaire marche sur Android le jour même et sur iPhone un ou deux jours plus tard.
  • Les codes sont publics. N’importe qui peut taper ALEX20, et c’est tout l’intérêt. Les conditions du programme interdisent les sites de codes promo et les achats avec son propre code, et les remboursements sont déduits des paiements suivants.
  • Pas de suivi des clics. Je sais quels codes ont vendu, pas qui est venu d’où. Pour une appli qui ne piste pas ses utilisateurs, ça me va très bien.

Bonus : valider les achats faits en dehors de ton appli

Celui-là est arrivé la même semaine. Si quelqu’un utilise un code promo Google Play dans le Play Store, l’achat se fait en dehors de ton appli, donc ton écouteur d’achats ne le voit jamais. Google rembourse tout achat qui n’est pas validé dans les 3 jours. Sur Android, HonorFit vérifie maintenant les achats existants au lancement et à chaque retour au premier plan, valide ceux qui ne le sont pas encore et débloque Pro.
