Affiliate-Codes für eine Indie-App ohne Backend

Ein versteckter In-App-Kauf pro Partner, und die Stores übernehmen die Buchhaltung. Von Thomas Willheim · 20. November 2026

Hey Leute. HonorFit ist der App-Blocker, bei dem du dir deine Bildschirmzeit mit Liegestützen verdienst, auf Ehrenwort. Es gibt keine Konten und keinen Server. Deine Daten bleiben auf deinem Handy, weil sie nirgendwo anders hinkönnen.

Dann hat mich ein Creator gefragt, ob ich ein Affiliate-Programm habe. Ich wollte eins: Er bekommt einen Code, seine Community bekommt 20 % Rabatt auf Pro Lebenslang, und er bekommt 50 % von dem, was ich verdiene, bei jedem Verkauf. Aber jedes Affiliate-System, das ich mir angeschaut habe, setzt ein Backend voraus, das Codes speichert, Klicks trackt und Käufe den Partnern zuordnet. Ich wollte nicht extra eins dafür bauen, und ich wollte erst recht nicht „nichts verlässt dein Handy“ dafür aufgeben.

Stattdessen habe ich Folgendes gemacht. Es funktioniert auf iPhone und Android, und es ist eine kleine Änderung an der Paywall plus ein Skript auf meinem Laptop.

Warum nicht die Promo-Codes der Stores?

Apple hat Angebotscodes, aber die Promo-Codes von Google Play für Einmalkauf-Produkte können den Artikel nur verschenken. Ein „20 % Rabatt“ gibt es nicht. Ich wollte einen einzigen Code, der in beiden Stores gleich funktioniert, also fielen die Codes der Stores raus.

Und selbst mit Rabatten gibt es ein zweites Problem: Ich muss jeden Monat wissen, von wessen Code jeder Verkauf kam, um die Leute zu bezahlen.

Der Trick: Jeder Partner bekommt sein eigenes Produkt

HonorFit verkauft Pro Lebenslang schon als Einmalkauf, honorfit_pro_lifetime, für 19,99 US$. Jeder Partner bekommt eine Kopie dieses Produkts mit seinem Code in der ID, für 15,99 US$:

honorfit_pro_lifetime            $19.99   (was alle sehen)
honorfit_pro_lifetime_p_alex20   $15.99   (nur mit dem Code ALEX20)

Diese eine Entscheidung erledigt die drei Aufgaben, die sonst ein Backend übernehmen würde:

  • Den Code prüfen. Der Code ist die Produkt-ID. Die App fragt den Store, ob es dieses Produkt gibt. Wenn ja, ist der Code echt.
  • Der Rabatt. Das ist einfach der Preis des Produkts, den der Store wie jeden anderen Preis für jedes Land anpasst.
  • Die Zuordnung. Die Verkaufsberichte von Apple und Google listen schon jeden Verkauf nach Produkt-ID auf. Ein Verkauf von ..._p_alex20 ist ein Verkauf von ALEX20.

Niemand sieht diese Produkte, ohne einen Code einzugeben. In-App-Käufe tauchen im Eintrag keines der beiden Stores auf, außer du entscheidest dich, sie zu bewerben. Die Partnerprodukte existieren also nur für Leute, die den Code kennen.

Die App-Seite

Die Paywall hat unter „Käufe wiederherstellen“ einen kleinen Link „Hast du einen Partnercode?“ bekommen. Wer darauf tippt, sieht ein Textfeld. Wenn jemand einen Code eingibt, bereinige ich ihn und frage den Store nach diesem Produkt. Ich nutze dafür expo-iap, aber mit StoreKit oder Play Billing direkt ist es dieselbe Idee:

const PARTNER_PREFIX = 'honorfit_pro_lifetime_p_';

// "alex-20 " -> "ALEX20". Viel mehr erlauben Produkt-IDs nicht.
export function normalizePartnerCode(input: string) {
  const code = input.replace(/[\s-]/g, '').toUpperCase();
  return /^[A-Z0-9]{3,20}$/.test(code) ? code : null;
}

export async function lookupPartnerCode(code: string) {
  const sku = PARTNER_PREFIX + code.toLowerCase();
  const products = await fetchProducts({ skus: [sku], type: 'in-app' });
  const product = products?.find((p) => p.id === sku);
  return product ? { code, sku, price: product.displayPrice } : null;
}

Wenn das Produkt zurückkommt, zeigt die Lebenslang-Karte 19,99 US$ 15,99 US$, und der Kaufbutton kauft das Produkt des Partners statt des normalen. Wenn nicht, sagt das Feld, dass der Code ungültig ist. Ein Store-Fehler hat eine eigene Meldung, damit ein Handy ohne Netz niemandem erzählt, sein echter Code sei falsch.

Das letzte Puzzleteil ist die Freischaltung. Überall, wo die App fragte „Ist das ein Pro-Produkt?“, hat sie früher mit einer Liste aus zwei IDs verglichen. Jetzt ist es eine Präfix-Prüfung, also behandeln der Kauf-Listener und „Käufe wiederherstellen“ einen Partnerkauf genau wie Lebenslang:

export const isProSku = (sku: string) =>
  sku === MONTHLY_SKU || sku === LIFETIME_SKU || sku.startsWith(PARTNER_PREFIX);

Weil die Codes gegen den Store geprüft werden, braucht ein neuer Partner nie ein App-Update. In der App gibt es keine Code-Liste, die ich aktuell halten müsste.

Die Produkte per API anlegen

Für jeden Partner von Hand ein Produkt in zwei Konsolen anzulegen, würde schnell nerven, also erledigt bun run affiliate add ALEX20 "Alex" "alex@example.com" beides:

App Store Connect

  1. Legt den In-App-Kauf (nicht verbrauchbar) mit der Produkt-ID des Partners an.
  2. Kopiert den Anzeigenamen und die Beschreibung des Lebenslang-Produkts in allen Sprachen.
  3. Setzt einen US-Basispreis von 15,99 US$. Apple rechnet daraus die anderen Länder aus.
  4. Kopiert die Länderverfügbarkeit von Lebenslang, lädt einen Screenshot für die Prüfung hoch und schreibt eine Prüfnotiz, die dem Prüfer genau sagt, wo das Codefeld ist und welchen Code er eingeben soll.

Dann schickt bun run affiliate submit ALEX20 es ans App Review. Jedes Partnerprodukt wird einzeln geprüft, meistens innerhalb von ein, zwei Tagen. Apple genehmigt nur einen In-App-Kauf, den der Prüfer auch wirklich erreichen kann, also muss das Codefeld zuerst in der veröffentlichten App sein.

Google Play

Mein erster Versuch nutzte den alten Endpoint inappproducts, der mit einem 403 und der Aufforderung zur Migration antwortete. Einmalkauf-Produkte liegen jetzt unter oneTimeProducts, wo ein Produkt eine oder mehrere Kaufoptionen hat. Das Skript:

  1. Kopiert die Store-Einträge und Steuereinstellungen von Lebenslang in ein neues Einmalkauf-Produkt.
  2. Lässt pricing:convertRegionPrices auf 15,99 US$ laufen, um einen Preis für jede Region zu bekommen.
  3. Legt eine Kaufoption mit diesen Preisen an und aktiviert sie dann mit purchaseOptions:batchUpdateStates.

Play-Produkte sind sofort live, ohne Prüfung.

Partner anhand der Store-Berichte auszahlen

Einmal im Monat holt bun run affiliate report 2026-11 die Berichte beider Stores und rechnet aus, was jeder Partner verdient hat:

  • Apple: der monatliche Sales-Summary-Bericht aus der App Store Connect API. Jede Zeile enthält die SKU, die Stückzahl und die Entwicklererlöse in der Währung des Käufers. Ich rechne die Erlöse zum Wechselkurs vom letzten Tag des Monats in US-Dollar um. Apple zahlt zu eigenen Kursen aus, das ist also eine Schätzung, aber nah genug dran, um danach auszuzahlen. (Stolperfalle: Fordere die Berichtsversion 1_0 an. 1_1 gab für diesen Bericht einen 400 zurück.)
  • Google: der monatliche Einnahmenbericht, ein Zip im Cloud-Storage-Bucket deiner Play Console. Er enthält schon jede Zahlung, Google-Gebühr, Steuer und Erstattung als eigene Zeile, also ergibt die Summe pro SKU den echten Nettobetrag.

Jeder Partner bekommt 50 % des Nettobetrags, mindestens null, und das Skript schreibt eine CSV, nach der ich auszahlen kann.

Play-Stolperfalle: Das Dienstkonto braucht in der Play Console die Berechtigung „Finanzdaten ansehen“, um Einnahmenberichte herunterzuladen. Nachdem ich sie aktiviert hatte, konnte das Konto die Dateien auflisten, bekam beim Herunterladen aber noch etwa einen Tag lang einen 403. Wenn das bei dir auch passiert, warte erst ab, bevor du anfängst, die Bucket-Berechtigungen zu ändern.

Die Kompromisse

  • Ein Produkt pro Partner. Für eine Handvoll Creator kein Problem. Für Hunderte bräuchtest du sowieso eine richtige Infrastruktur.
  • Jedes Apple-Produkt wird geprüft. Der Code eines neuen Partners funktioniert auf Android am selben Tag und auf dem iPhone ein, zwei Tage später.
  • Die Codes sind öffentlich. Jeder kann ALEX20 eingeben, und genau darum geht es. Die Programmbedingungen schließen Gutscheinseiten und Käufe mit dem eigenen Code aus, und Erstattungen werden von späteren Auszahlungen abgezogen.
  • Kein Klick-Tracking. Ich weiß, welche Codes verkauft haben, nicht, wer woher kam. Für eine App, die ihre Nutzer nicht trackt, ist mir das recht.

Bonus: Käufe außerhalb deiner App bestätigen

Das kam in derselben Woche auf. Wenn jemand einen Google-Play-Promo-Code im Play Store einlöst, passiert der Kauf außerhalb deiner App, also bekommt dein Kauf-Listener ihn nie mit. Google erstattet jeden Kauf, der nicht innerhalb von 3 Tagen bestätigt wird. HonorFit prüft auf Android jetzt beim Start und jedes Mal, wenn die App wieder in den Vordergrund kommt, auf vorhandene Käufe, bestätigt die noch unbestätigten und schaltet Pro frei.
