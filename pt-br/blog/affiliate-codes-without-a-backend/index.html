Códigos de afiliado para um app indie sem backend

Uma compra no app oculta por parceiro, e as lojas cuidam da contabilidade. Por Thomas Willheim · 20 de novembro de 2026

Oi, gente! O HonorFit é o bloqueador de apps em que você ganha seu tempo de tela fazendo flexões, no sistema de honra. Ele não tem contas nem servidor. Seus dados ficam no seu celular porque não têm para onde ir.

Aí um criador de conteúdo me perguntou se eu tinha um programa de afiliados. Eu queria ter um: a pessoa ganha um código, o público dela ganha 20% de desconto no Pro Vitalício e ela fica com 50% do que eu ganho em cada venda. Só que todo sistema de afiliados que eu olhei pressupõe um backend que guarda códigos, rastreia cliques e liga as compras aos parceiros. Eu não queria construir um só para isso, e muito menos quebrar o “nada sai do seu celular” para fazer isso.

Então fiz outra coisa. Funciona no iPhone e no Android, e é uma pequena mudança no paywall mais um script no meu notebook.

Por que não usar os códigos promocionais das próprias lojas?

A Apple tem códigos de oferta, mas os códigos promocionais do Google Play para produtos de compra única só conseguem dar o item de graça. Não existe “20% de desconto”. Eu queria um código só que funcionasse igual nas duas lojas, então os códigos das lojas ficaram de fora.

E mesmo com desconto, tem um segundo problema: eu preciso saber de quem era o código de cada venda, todo mês, para pagar as pessoas.

O truque: cada parceiro ganha seu próprio produto

O HonorFit já vende o Pro Vitalício como compra única, honorfit_pro_lifetime, por US$ 19,99. Cada parceiro ganha uma cópia desse produto com o código dele no ID, a US$ 15,99:

honorfit_pro_lifetime            $19.99   (o que todo mundo vê)
honorfit_pro_lifetime_p_alex20   $15.99   (só com o código ALEX20)

Essa única decisão resolve as três tarefas que um backend normalmente faria:

  • Verificar o código. O código é o ID do produto. O app pergunta à loja se esse produto existe. Se existe, o código é real.
  • O desconto. É só o preço do produto, que a loja adapta para cada país como qualquer outro preço.
  • A atribuição. Os relatórios de vendas da Apple e do Google já listam cada venda por ID de produto. Uma venda de ..._p_alex20 é uma venda do ALEX20.

Ninguém vê esses produtos a menos que digite um código. Compras no app não aparecem na página de nenhuma das lojas, a não ser que você escolha promovê-las, então os produtos de parceiro só existem para quem conhece o código.

O lado do app

O paywall ganhou um pequeno link “Tem um código de parceiro?” embaixo de Restaurar compras. Tocar nele mostra um campo de texto. Quando alguém digita um código, eu limpo o texto e peço esse produto para a loja. Aqui eu uso o expo-iap, mas a ideia é a mesma com StoreKit ou Play Billing direto:

const PARTNER_PREFIX = 'honorfit_pro_lifetime_p_';

// "alex-20 " -> "ALEX20". IDs de produto não aceitam muito mais que isso.
export function normalizePartnerCode(input: string) {
  const code = input.replace(/[\s-]/g, '').toUpperCase();
  return /^[A-Z0-9]{3,20}$/.test(code) ? code : null;
}

export async function lookupPartnerCode(code: string) {
  const sku = PARTNER_PREFIX + code.toLowerCase();
  const products = await fetchProducts({ skus: [sku], type: 'in-app' });
  const product = products?.find((p) => p.id === sku);
  return product ? { code, sku, price: product.displayPrice } : null;
}

Se o produto volta, o card do Vitalício mostra US$ 19,99 US$ 15,99 e o botão de compra compra o produto do parceiro em vez do normal. Se não volta, o campo avisa que o código não é válido. Um erro da loja tem sua própria mensagem, para que um celular sem internet não diga a ninguém que o código verdadeiro dele é falso.

A última peça é a liberação do acesso. Em todo lugar onde o app perguntava “isso é um produto Pro?”, ele comparava com uma lista de dois IDs. Agora é uma verificação de prefixo, então o listener de compras e o Restaurar compras tratam uma compra de parceiro exatamente como o Vitalício:

export const isProSku = (sku: string) =>
  sku === MONTHLY_SKU || sku === LIFETIME_SKU || sku.startsWith(PARTNER_PREFIX);

Como os códigos são verificados na loja, adicionar um parceiro nunca exige atualizar o app. Não existe nenhuma lista de códigos dentro do app para manter em dia.

Criando os produtos pela API

Criar um produto na mão em dois consoles para cada parceiro ia cansar rápido, então bun run affiliate add ALEX20 "Alex" "alex@example.com" faz as duas coisas:

App Store Connect

  1. Cria a compra no app (não consumível) com o ID de produto do parceiro.
  2. Copia o nome de exibição e a descrição do produto Vitalício em todos os idiomas.
  3. Define um preço base de US$ 15,99 nos EUA. A Apple calcula os outros países a partir dele.
  4. Copia a disponibilidade por país do Vitalício, sobe uma captura de tela para a revisão e escreve uma nota de revisão que diz ao revisor exatamente onde fica o campo do código e qual código digitar.

Depois, bun run affiliate submit ALEX20 manda o produto para o App Review. Cada produto de parceiro é revisado separadamente, normalmente em um ou dois dias. A Apple só aprova uma compra no app que o revisor consiga de fato alcançar, então o campo do código precisa estar no app publicado primeiro.

Google Play

Minha primeira tentativa usou o endpoint antigo inappproducts, que devolveu um 403 mandando eu migrar. Produtos de compra única agora ficam em oneTimeProducts, onde um produto tem uma ou mais opções de compra. O script:

  1. Copia as páginas e as configurações de impostos do Vitalício para um novo produto de compra única.
  2. Roda pricing:convertRegionPrices em US$ 15,99 para ter um preço para cada região.
  3. Cria uma opção de compra com esses preços e depois a ativa com purchaseOptions:batchUpdateStates.

Os produtos do Play entram no ar na hora, sem revisão.

Pagando os parceiros com os relatórios das lojas

Uma vez por mês, bun run affiliate report 2026-11 puxa os relatórios das duas lojas e calcula quanto cada parceiro ganhou:

  • Apple: o relatório mensal Sales Summary da App Store Connect API. Cada linha tem o SKU, as unidades e a receita do desenvolvedor na moeda do comprador. Eu converto a receita para dólares americanos pelo câmbio do último dia do mês. A Apple paga com as próprias taxas de câmbio, então é uma estimativa, mas chega perto o bastante para pagar com base nela. (Pegadinha: peça a versão de relatório 1_0. A 1_1 devolveu um 400 para esse relatório.)
  • Google: o relatório mensal de ganhos, um zip no bucket do Cloud Storage do seu Play Console. Ele já traz cada cobrança, taxa do Google, imposto e reembolso em linhas separadas, então somar tudo por SKU dá o líquido real.

Cada parceiro fica com 50% do líquido, com mínimo de zero, e o script gera um CSV que eu uso para pagar.

Pegadinha do Play: a conta de serviço precisa da permissão “Ver dados financeiros” no Play Console para baixar os relatórios de ganhos. Depois que eu ativei, a conta conseguia listar os arquivos, mas continuou levando 403 ao baixá-los por cerca de um dia. Se acontecer com você, espere antes de sair mexendo nas permissões do bucket.

Os prós e contras

  • Um produto por parceiro. Tranquilo para um punhado de criadores. Para centenas, você ia querer uma infraestrutura de verdade de qualquer jeito.
  • Todo produto da Apple passa por revisão. O código de um parceiro novo funciona no Android no mesmo dia e no iPhone um ou dois dias depois.
  • Os códigos são públicos. Qualquer um pode digitar ALEX20, e a ideia é essa mesma. As regras do programa proíbem sites de cupons e comprar com o próprio código, e reembolsos são descontados de pagamentos futuros.
  • Sem rastreamento de cliques. Eu sei quais códigos venderam, não quem veio de onde. Para um app que não rastreia os usuários, por mim tudo bem.

Bônus: confirme as compras feitas fora do seu app

Isso apareceu na mesma semana. Se alguém resgata um código promocional do Google Play na Play Store, a compra acontece fora do seu app, então o seu listener de compras nunca fica sabendo. O Google reembolsa qualquer compra que não seja confirmada em 3 dias. Agora, no Android, o HonorFit procura compras já feitas ao abrir e sempre que volta para o primeiro plano, confirma as que ainda não foram confirmadas e libera o Pro.

Quer um código?
